# 技术选型与架构

状态：主技术栈已确认，设备接口与播放样机待验证

版本：0.4

## 1. 架构结论草案

建议采用“Windows 主控应用 + 独立播放输出进程 + 设备适配器”的本地优先架构。

控制界面和 LED 输出必须是两个独立窗口；进一步建议将播放输出拆为独立进程。这样控制界面崩溃或重载时，不会直接把桌面、弹窗或开发错误暴露到主屏，也便于以后为 DJ 小屏增加独立输出进程。

```text
Windows 主控界面
  ├─ 节目/歌单/素材/文字管理
  ├─ 播控编排与状态机
  ├─ 本地数据库与操作日志
  ├─ Qu-16 设备适配器
  ├─ Tiger Touch Pro 设备适配器
  └─ 本地消息通道
       ├─ 主 LED 播放输出进程
       └─ DJ 小屏输出进程（后续）

局域网 API（后续）
  └─ 手机点歌、弹幕、祝福与审核
```

现场物理设备必须按三条独立链路建模，详见 [现场硬件拓扑基线](hardware/site-topology.md)：

```text
AUDIO：Shure SLX4 → Qu-16 → DP448 → 多台功放 → 全场音箱
LIGHT：Tiger Touch Pro → DMX512 → DSP8 Splitter ×3 → 全场灯具
VIDEO：中控电脑 mpv → Windows 视频输出 → LED 视频系统 → 全场屏幕
```

其中 DSP8 是灯光 DMX splitter，禁止出现在音频设备图或人声处理链中。

### 离线开发与现场验收分层

实体 Qu-16 不在开发现场时，不阻塞 Vocal Engine 的软件开发。开发环境提供 48 kHz/float32 虚拟 Qu-16 USB 后端，可重放真实 WAV、生成确定性测试人声，并注入 underrun、disconnect 和 CPU overload。F0、音准比较、DSP 修正、Formant、Adaptive Mixer 及后续局部补声均应先通过同一回放样本的自动回归和响度匹配 A/B。

状态必须使用以下四级，不得把模拟证据升级为现场结论：

```text
IMPLEMENTED        已实现但尚未完成模拟门
SIMULATION_PASSED  确定性回放与故障注入通过
HARDWARE_PENDING   软件已具备，等待 Qu-16/现场硬件验证
SITE_VERIFIED      已完成真实 USB 路由、RTT、安全旁路和长时现场验收
```

真实 Qu-16 仍是 USB 通道映射、驱动 buffer、物理 RTT、时钟稳定性、耳返体感和拔线/杀进程 fallback 的硬门，但不是编写算法和 UI 的前置条件。

## 2. 关键边界

### 视频

软件负责本地视频解码、渲染、异形屏内容适配和全屏输出。Windows 将 LED 接收/发送系统识别为第二显示器；软件只面向其像素画布，不直接面向毫米尺寸。

现场已确认 LED 可作为普通 Windows 显示器即插即用，现有普通视频能够完整显示在异形发光区域。因此首版不集成 LED 发送卡或配屏软件协议，也不修改模组走线和接收卡参数。

主控实时预览应复用最终合成结果的缩放画面，避免“预览正确、主屏错误”。异形区域采用可配置遮罩与安全区，不把屏幕形状写死在 UI 代码中。

根据 P2.5 横向模组参数与 2026-08-25 用户确认的 5120 × 5760 mm 总尺寸，逻辑布局为：

```text
外框逻辑画布：2048 × 2304 px

上半区：空白 512 × 1152 | A 1024 × 1152 | 空白 512 × 1152
下半区：                B 2048 × 1152
```

- B 区：16 × 18 个模组，共 288 个
- A 区：8 × 18 个模组，共 144 个
- 总计：432 个模组
- 实际发光像素：3,538,944 px
- 外框画布像素：4,718,592 px，其中上方左右区域必须透明或黑色

该 T 形比例已由用户再次确认。UI `UI-R03 / C1` 使用统一 LED 遮罩预览，外框固定为 8:9；渲染和截图测试不得退化为 16:9 预览。

软件内部保留 2048 × 2304 的异形逻辑布局，但不把显卡输出分辨率写死为该值。当前现场 `LED_HDMI` 暴露 1920 × 1080，DVP 处理器按完整 HDMI 栅格映射到 5120 × 5760 mm 物理墙；应用因此把 8:9 逻辑合成层横向预拉伸 2 倍并铺满 1920 × 1080。处理器映射后恢复正确 8:9 比例。若只居中发送 960 × 1080，物理墙只能点亮 2560 mm 宽，B 区左右会各留 1280 mm 黑边。

首次启动流程：

1. 枚举 Windows 当前所有活动显示器。
2. 在设置页显示名称、分辨率、刷新率、位置和主/副屏标识。
3. 操作员在预览测试后选择 LED 屏。
4. 保存较稳定的显示器设备标识，而不是只保存“第二屏”序号。
5. 后续启动时自动匹配；如果设备缺失，不把节目误投到操作屏，而是报警并保持输出关闭。

### 2026-08-20 第二屏输出里程碑

第一阶段已在 Tauri 桌面端实现 Windows 活动显示器枚举和独立 `output` 窗口。程序启动时自动排除主控窗口所在显示器；找到独立显示器后，在该屏创建无边框、无任务栏、置顶的全屏窗口，同时保持 C1 实时预览持续可见。若只检测到一台显示器，独立输出窗口保持隐藏，节目画面由 C1 实时预览承接，禁止把输出窗口回退到操作屏。

主控的 PGM 状态通过 Rust 托管状态和 Tauri 事件发送给输出窗口。只有“确认上屏”后的媒体及画面变换参数会同步；素材悬停、PVW 编辑和取消操作不影响现场屏幕。输出窗口启动时先显示安全黑场，再读取最后一次 PGM 状态，避免初始化期间暴露桌面。

当前桌面版已用真实 MP4 验证 C1 PVW、确认上屏、PGM 输出和视频音轨独立开关，并用两个 mpv/JSON IPC 进程承载 Deck 1/2 的真实音频播放、Seek 与手动混音。输出画面仍由独立 WebView 合成，以便统一承载异形遮罩、视频、图片和文字叠加层；正式版本必须迁移到 `libmpv` 单次硬件解码、多渲染面的 GPU 管线，C1/PVW 不得通过低帧率截图代替实时视频。

第二屏采用即插即用策略：原生桌面启动层首先请求 Windows 切换到扩展桌面，再检查主控屏以外的已连接显示器，发现后立即按已保存的 LED 传输预设恢复 PGM；应用运行期间再由 5 秒心跳负责断开和热插拔恢复。软件只负责从复制切换到扩展，不修改任何显示器的分辨率、缩放、刷新率或宽高比。大屏断开后立即退出全屏并隐藏预加载输出窗口，C1 实时预览继续工作；更换或重新插入大屏后重新读取显示器位置与当前分辨率、恢复第二屏全屏，并与 C1 同时显示最后确认的 PGM。普通显示器只按固定 16:9 传输画布等比例预览并留黑边，不得拉伸或覆盖昨晚确认的 `2048×2304` 逻辑画布和 `5120×5760 mm` 物理比例。整个恢复流程不依赖开发工具或人工重新启动，且任何时候都禁止把可见输出移动到主控屏。

软件提供“测试图”功能，用于显示边界框、中心线、A/B 区域、像素网格和编号，以便现场检查裁切、缩放和屏幕映射。

### 2026-08-22 图文预览与输出一致性基线

图文叠加层不得使用 C1 窗口或第二屏窗口各自的 `vw`、固定 CSS 像素来决定元素大小。C1 的 PGM/PVW 与独立输出窗口统一从 `2048 × 2304` 逻辑画布渲染，文字、PNG、SVG、坐标、缩放和阴影均先落在该逻辑坐标系，再按各自可视画布整体等比缩放。由此保证控制台预览较小时，文字在第二屏上的归一化位置和占屏比例仍一致。

自动回归入口为 `npm run test:desktop-text-parity`。测试在不同尺寸的 C1 与物理输出窗口之间比较每个图文元素归一化后的中心坐标、宽度和高度，允许误差小于 0.6%。该测试只校验合成几何一致性；不同显示器的 DPI、子像素排列和 LED 处理器二次缩放仍可能造成边缘观感差异。

### 2026-08-25 现场 LED 视频处理器验收

- Windows 识别主控屏和 `LED_HDMI`（DVP）视频处理器，后者当前为 1920 × 1080、100% 缩放。
- 现场物理墙为 5120 × 5760 mm（8:9），逻辑画布为 2048 × 2304；处理器使用完整 1920 × 1080 输入栅格。软件输出端横向预拉伸 2 倍覆盖全栅格，因此 HDMI 抓帧中的测试格应为 2:1 横向矩形，经处理器映射到实体屏后恢复为方格。
- 输出窗口按副屏物理坐标和物理尺寸创建，强制使用 Win32 `WS_POPUP` 全屏置顶窗口覆盖任务栏，并关闭 Windows 11 圆角和 DWM 边框；5 秒输出状态心跳会重新校正全屏、置顶和物理边界，防止多屏任务栏被 Windows Shell 再次抬到节目画面上方。
- 真实 MP4 经 PVW/确认上屏后显示在 T 形 LED 可视区域，非 LED 区保持纯黑；C1 实时预览始终保留。
- 实测执行“仅电脑屏幕 → 扩展”后，输出窗口会自动隐藏和恢复，不会误投主控屏，也不需要重启软件。
- 自动回归入口为 `npm run test:desktop-output`，同时校验输出目标不是主控屏、输出窗口可见、逻辑视口乘 DPI 等于目标物理分辨率。

### 音频

软件负责歌曲媒体播放。每首歌的“原唱”是导入的原始完整混音；“伴唱”优先使用供应商/人工提供的正式伴奏文件，没有正式伴奏时使用 Demucs 导入分析生成的 `no_vocals` 音轨。Demucs 同时输出 `vocals` 人声音轨，供 MOSS-Music 歌词识别与原生时间轴生成使用。两条派生音轨按媒体指纹和分离模型版本持久化，禁止在播放时现场分离。

为保证切换时不重启或跳时，导入工作器需把原始混音与伴奏规范化到相同采样率、起点和总采样数，并生成包含多音轨的播放代理；mpv 在同一个 Deck 内切换音轨 ID，继续使用原 `time-pos`。若派生音轨长度或延迟校验失败，该歌曲必须保持原唱并把伴唱按钮标为不可用，不能假装切换成功。

### 音乐供应商接入

采用可替换的 `MusicProvider` 适配层，播放编排不能直接依赖 QQ 音乐或酷狗的内部接口：

```text
MusicProvider
  ├─ Search(query)
  ├─ GetMetadata(trackId)
  ├─ GetPlaybackEntitlement(trackId)
  ├─ PreparePlayback(trackId)
  ├─ GetLyrics(trackId)
  └─ GetVocalModes(trackId)

实现候选
  ├─ LicensedOnlineProvider（取得正式 B 端合同/API 后）
  └─ AuthorizedLocalLibrary（合法授权的本地应急曲库）
```

`PreparePlayback` 的结果可以是短期流地址、供应商 SDK 播放句柄或加密离线缓存，不假设供应商会交付普通 MP3 文件。任何资源都同时保存供应商、授权状态、到期时间、地域/设备限制和可用音轨信息。

明确排除：调用逆向得到的私有 API、模拟登录、读取客户端缓存、解密会员下载、抓取播放地址或用界面自动化批量下载。这些方案违反平台规则的风险高，接口随时失效，也无法证明酒吧公开播放授权。

如果供应商只允许在其官方客户端中播放，可以把该客户端作为人工应急工具，但不纳入 KING CLUB 软件的自动播控承诺；键盘媒体键或窗口自动化既不能解决版权授权，也无法可靠获得歌单状态、原伴唱和播放确认。

### Qu-16

Qu-16 官方 MIDI 协议支持 USB-B MIDI，也支持经 Network 口的 TCP MIDI，可双向发送和接收控制变化。网络模式只允许一个 TCP MIDI 连接，因此软件必须考虑连接独占、心跳和断线重连。

首选连接方案待现场验证：

1. 网络 TCP MIDI：布线灵活，可查询/同步更多状态；需要固定 IP 和可靠局域网。
2. USB MIDI：链路简单；受 USB 距离、驱动和主控电脑物理位置限制。

软件只开放明确列入白名单的通道、Mute、Fader 或 Scene 操作，避免误控现场其他音频通道。

规划中的低延迟人声增强使用独立 Vocal Engine：SLX4 先以模拟音频进入 Qu-16，指定通道通过 USB 送入电脑，处理结果再由独立 USB Return 返回 Qu-16。Qu-16 的总混音随后按现场链路进入 DP448、功放和音箱。电脑进程、USB 或处理链故障时必须保留 Qu-16 内部安全 dry path，不得让 DP448 后方的 PA 链随电脑一起失声。

### DP448 与功放链

现场正面照片已确认一台标注 `DP448 Audio Management System` 的设备，并可见 A-D 四路输入和 1-8 八路输出选择，连接在 Qu-16 下游及多台功放上游。品牌、背板接口、控制协议及现有 DSP 配置仍需以铭牌、控制软件和配置备份核对。DP448 是系统音频处理节点，不是调音台，也不是电脑 USB 实时人声接口。

### Tiger Touch Pro

灯光台继续作为灯具和 DMX/Art-Net 的唯一权威控制器。本软件只触发已经在灯光台编排好的 Cue、Playback 或 Macro，不在首版直接生成灯具级 DMX 数据。

具体触发方式必须依据控制台序列号、Titan 版本和当前 show 配置做技术验证，候选包括灯光台支持的远程、MIDI或网络触发能力。不可在未验证协议时承诺全自动控制。

Tiger Touch Pro 的 DMX512 下游已确认连接 3 台 DSP8 Splitter，再分配到全场灯具。DSP8 的厂商、完整型号、Universe、各输出灯具链和地址范围待现场清点；软件模型必须把它们归入 LIGHT，不能误作音频 DSP 或音频分配器。

## 3. 技术栈方案

### 已确认：Rust 核心 + Tauri 2 控制台 + mpv 播放进程

Rust 适合承担需要长期稳定运行的核心逻辑，但不要求所有 UI 都使用纯 Rust 绘制。建议技术栈：

- Rust stable/MSVC：领域模型、播放编排、设备适配器、状态恢复和日志
- Tokio：异步任务、外设连接、心跳和进程通信
- Tauri 2：Windows 控制台应用外壳
- React + TypeScript + Vite：简单、密集、易维护的控制台 UI
- mpv 独立进程 + JSON IPC：视频/音频解码、音轨控制和屏幕输出
- SQLite：节目、歌单、素材索引、绑定关系、设置和日志
- rusqlite + bundled SQLite：首版 Rust 数据访问层，随桌面程序离线部署，不依赖数据库服务
- Axum：后续手机点歌、弹幕和审核所需的局域网 HTTP/WebSocket 服务
- Serde：命令、状态和配置序列化
- tracing：结构化日志与故障诊断

### Windows 播放器指令集与硬件解码基线

- 当前 i7-9750H 开发机继续使用 `x86-64-v3` 版 mpv。V3 需要 AVX2/FMA/BMI2，可保证日常开发、自动测试与桌面调试不中断。
- 正式酒吧主控机以 `x86-64-v4` 为采购与部署目标，CPU 必须完整支持 AVX-512 相关的 x86-64-v4 指令集。V4 不改变功能边界，也不改变 GPU 硬件解码管线。
- 当前固定的上游 Windows 发布源没有提供现成 V4 成品，因此生产 V4 必须由项目自行构建、锁定源码与依赖、记录 SHA-256，并完成长时播放和目标主机实测后才可随安装包交付。
- V3 与 V4 共用相同的 Rust、Tauri、JSON IPC 和媒体逻辑，不需要维护两套业务代码；开发版使用 V3，生产发布版替换为经过校验的 V4 播放内核。
- 视频解码优先启用 GPU 硬件解码；CPU 指令集版本仍决定 mpv 程序本身能否启动，两者不能互相替代。
- 部署程序必须在安装或启动检查中识别 CPU 能力，禁止把不兼容的播放器变体静默安装到现场主机。

Tauri 在 Windows 上使用系统 WebView2 渲染控制界面。Deck 1/2 音频由独立 mpv 进程承担；节目视频的目标架构是 `libmpv` 单次 GPU 硬件解码，并把同一已解码帧呈现到第二屏和 C1 实时预览。禁止用两个 WebView 视频播放器重复解码同一个节目，也禁止用低帧率截图流冒充实时预览。

### 为什么适合本项目

- Rust 类型系统适合约束播放状态机、设备指令和错误处理
- 单个核心可复用到桌面端、后续局域网服务和设备适配器
- Tauri 控制台比 Electron 更轻，UI 又比纯 Rust 桌面框架更容易快速调整
- React/TypeScript 足以完成朴素的控制台，无需动画、3D 或复杂视觉特效
- mpv 已具备成熟的硬件解码、音轨/声道选择和 JSON IPC，避免自行编写解码器
- 播放进程与 UI 分离后，可以独立监控、重启，并为未来 DJ 小屏启动第二个输出实例

### 不采用的方向

- 不用纯前端 `<video>` 元素承担正式 LED 播放：多文件组合、独立音轨、多屏和故障恢复能力不足
- 不在首版自行用 FFmpeg/wgpu 从零编写完整播放器：工作量和稳定性风险过高
- 暂不选择 Slint/egui 等纯 Rust UI：它们可以实现界面，但当前控制台包含大量列表、表格、搜索和表单，Web UI 的开发与维护效率更好
- .NET/WPF 保留为样机失败时的备选，不再作为当前首选

### 必须先通过的技术样机

先用最小样机验证 Rust 对 mpv 的管理和 Tauri 状态同步：

- 在指定第二屏独占全屏
- 主控窗口实时预览
- 4K 或现场实际规格视频连续播放
- 暂停、跳转、无黑帧切换和循环
- 音轨/声道切换
- MP4 音频搭配替换视频、MP3 搭配循环视频
- UI 关闭或重启时播放输出的预期行为
- 输出进程异常后的安全黑场与自动恢复

技术栈已由 [ADR 0001](decisions/0001-rust-tauri-react-mpv.md) 正式接受。样机用于确定 mpv 集成和媒体组合细节；如果多源同步或实时预览不达标，优先比较 libmpv Render API 或 GStreamer，不直接推翻 Rust/Tauri/React 主技术栈。

## 4. 核心领域模型

- `MediaAsset`：歌曲、视频、图片或音频素材
- `Song`：歌曲元数据、默认音频来源、默认画面来源及原声/伴唱配置
- `AudioSource`：MP4 音轨、独立 MP3/FLAC/WAV 或后续授权流媒体
- `VisualSource`：原 MP4 视频、自有视频、静态图片或默认背景
- `MediaComposition`：音频、画面、循环、裁切、回退和同步策略
- `LightingPreset`：灯光台 Cue/Playback 的逻辑引用
- `ScreenLayout`：物理屏、像素画布、异形遮罩和安全区
- `ProgramTemplate`：星期节目模板
- `Playlist`：常规或特别歌单，包含草稿/发布版本、标签和累计时长
- `WeeklySchedule`：星期一至星期日与默认常规歌单的映射
- `PlaylistItem`：歌曲及其视频、灯光、文字绑定
- `PlaybackSession`：当前队列、播放模式、位置和状态
- `Deck`：A/B 播放槽，分别持有媒体组合、时钟、音量和预加载状态
- `TransitionPlan`：两 Deck 之间的音频曲线、视频转场、时长和灯光触发点
- `MixPoint`：歌曲默认或歌单条目覆盖的 IN/OUT 时间点及来源（人工/自动建议）
- `Device`：主屏、调音台、灯光台等连接配置
- `CommandLog`：操作与外设指令审计

歌曲、视频和灯光之间不应做固定一对一关系。一首歌有默认组合，但单次播放可以覆盖；同一视频和灯光预设也可被多首歌复用。

歌曲播放不能直接把一个文件交给播放器窗口，而应先生成组合计划：

```text
Song + PlaylistItem 覆盖配置
  → 解析 AudioSource
  → 解析 VisualSource
  → 生成 MediaComposition
  → 播放引擎同步启动声音和画面
```

播放内核技术验证必须覆盖两种管线：单个 MP4 的音视频同步播放，以及从不同文件解码音频和视频后使用同一播放时钟同步。后者是“MP3 + 自有视频”和“MP4 音频 + 替换视频”的基础，也是 LibVLCSharp/mpv 选型的关键测试项。

当自有视频循环时只循环视频轨，不能重启音频；切换原声/伴唱时也不能重启画面。播放结束时间始终以歌曲音频为准。

运行时控制通过统一 `PlaybackCommand` 进入编排器，不允许 UI 直接操作播放器或外设：

- `Play`、`Pause`、`Stop`、`Seek`
- `Previous`、`Next`、`SetPlaybackMode`
- `SetVocalMode`
- `SetVisualSource`
- `SetMute`、`SetVolume`
- `Standby`、`Blackout`

命令携带唯一 ID 并进行幂等处理，避免按钮连点造成重复切歌。编排器返回“已接收、执行中、成功或失败”，UI 按真实结果更新，而不是点击后直接假设成功。

歌单定义与播放队列分离：

- `PlaylistRevision` 保存可编辑的歌单版本
- `PublishedPlaylist` 是营业使用的已发布快照
- `PlaybackQueue` 是一次播放会话的运行副本，可临时插播、跳过或调序
- 播放中的临时调整默认不反向修改歌单模板
- 应用新发布版本时，由操作员决定立即重建后续队列或下次营业生效

每次队列变更后重新计算总时长、已播放时长、剩余时长和预计结束时间。8 小时是内容覆盖和连续运行测试的最低要求，不应通过复制同一文件来掩盖曲库不足。

## 5. 播放状态与一致性

核心播放状态建议统一为：`Idle → Loading → Ready → Playing ↔ Paused → Stopping → Idle`，并增加 `Faulted` 安全状态。

播放引擎包含两个独立 Deck 状态机。编排器维护 `ActiveDeck` 和 `StandbyDeck`：当前 Deck 播放时，待播 Deck 进入 `Preloading → Ready`；只有待播资源达到 Ready 后才允许自动过渡。

每次切歌由编排器生成一次事务式执行计划：

1. 预加载下一首音视频。
2. 验证绑定的设备和灯光预设是否可用。
3. 按配置的时间点切换音视频。
4. 触发灯光预设。
5. 记录每个步骤的实际结果；单个外设失败不应导致播放进程崩溃。

### 双 Deck 过渡引擎

Crossfader 位置标准化为 `0.0`（仅 A）至 `1.0`（仅 B）。音频默认使用等功率曲线，而不是简单线性音量：

```text
gainA = cos(position × π / 2)
gainB = sin(position × π / 2)
```

视频转场和音频交叉淡化使用同一过渡时间轴，但曲线可以不同。灯光触发作为时间轴事件，不与音视频是否成功解码耦合。

每个 Deck 使用歌曲的有效播放区间 `[IN, OUT]`。待播 Deck 从 IN 点开始，当前 Deck 在 OUT 点触发过渡；媒体文件本身不做破坏性裁剪。自动分析只能生成建议值，人工确认值优先，歌单条目的临时覆盖优先于歌曲默认值。

mpv 集成需要验证两种实现：

1. 两个受控 mpv 实例分别承担 Deck A/B，由 Rust 编排音量和画面切换。
2. 如果双实例画面合成或实时预览不满足要求，使用 libmpv Render API 或专用合成层。

任何实现都必须保证 LED 只暴露一个稳定的全屏输出窗口；不能在切换时让两个顶层窗口争夺焦点或闪出桌面。

UI 必须分别显示“准备发送/已发送”和“设备已确认/未确认”，不能用按钮高亮假装设备已经执行。

播放会话需要周期性持久化：当前歌单及版本、队列顺序、当前条目、媒体位置、播放模式、原伴唱状态和临时插播栈。异常重启后先恢复为暂停/待确认状态，不能在无人确认时直接向酒吧大屏和音响自动续播。

## 6. 数据与素材

- 首版使用嵌入式 SQLite，不部署 MySQL。SQLite 保存配置、播放列表、素材索引、分析状态和派生数据索引；MP3、FLAC、MP4 等媒体二进制仍保存在硬盘素材目录
- 分析缓存以“规范化路径 + 文件大小 + 修改时间/内容指纹 + 音轨 + 算法版本”为唯一键。缓存命中直接读取；文件新增、内容变化或算法升级时才重新分析
- 波形峰值、BPM、Beat/Downbeat/Bar 时间点等小型结构化结果可压缩存入 SQLite BLOB；封面、LRC、预览代理和较大的中间文件放缓存目录，SQLite 只保存路径与状态
- 媒体保存在可配置的本地素材目录
- 使用稳定 ID 和相对/受管路径，避免盘符变化后全部失效
- 导入时读取格式、时长、分辨率、帧率、音轨和校验信息
- 缩略图与预览代理文件放入独立缓存，可重建
- AI 分离结果保存在按媒体指纹划分的派生目录：至少包含 `vocals`、`no_vocals`、分离清单及原唱/伴唱多音轨播放代理；SQLite 只保存路径、来源优先级、模型版本、校验状态和失败原因
- 需要备份数据库、屏幕映射、设备配置和节目模板

### 视频素材清晰度基线

- 主 LED 的异形逻辑画布为 2048 × 2304；当前 Windows 副屏链路为 3840 × 2160，其中居中的 8:9 有效输出约为 1920 × 2160。
- 16:9 视频使用“铺满”时按画布高度缩放并裁切左右两侧。建议素材至少为 3840 × 2160；最理想是按 2048 × 2304 异形画布直接制作，或使用 4096 × 2304 的 16:9 素材。
- 1920 × 1080 只作为兼容下限；低于 1080p 的素材应在导入和上屏前提示“低清素材”。960 × 540 在当前屏幕上会被放大约 4 倍，不适合作为现场节目素材。
- 输出窗口不得额外应用饱和度、对比度或锐化 CSS 滤镜，避免触发二次合成并强化低清素材边缘；颜色处理应由素材制作流程或正式 GPU 视频管线完成。

### 音频波形分析与缓存

正式波形由 Rust 后端在导入媒体时生成，前端不在播放过程中实时解码完整媒体：

1. 导入 MP3、FLAC 或 MP4 时，Rust 后端通过选定的媒体解码层读取目标音轨并解码为 PCM；MP4 必须使用实际播放的音轨，不能从视频亮度或容器码率推算波形。
2. 按固定时间窗口聚合 PCM 样本，至少提取每个窗口的峰值；可选同时计算 RMS，用于更稳定地表达听感能量。
3. 将窗口结果继续降采样为适合 UI 各缩放级别的 `peaks` 数据，保留声道合并策略、采样窗口和分析版本等元数据。
4. 以媒体指纹作为缓存键保存波形。指纹至少能够识别文件内容或内容变化，并结合所选音轨与分析算法版本；文件被替换、音轨改变或算法升级时自动失效重建。
5. UI 只读取缓存的 `peaks` 绘制 Deck 波形，并在播放时叠加当前位置、已播放区域和可选 IN/OUT 标记；UI 不重复解码 MP3/MP4。
6. C2 双 Deck 波形使用 Canvas 渲染。媒体播放引擎的已确认位置是 UI 唯一的进度来源；Canvas 只绘制固定中央播放线附近约 12 秒的真实时间窗口，不生成整条波形的数千个 DOM 柱状元素。固定的是可视时间窗口，不是每首歌曲的峰值总数。
7. 峰值总数按歌曲时长计算并设置合理上限：歌曲越长，持久化峰值越多；Canvas 再按当前窗口和实际像素宽度抽样绘制。因此短歌、长歌和一小时混音保持相近的像素/秒移动速度，不会把整首长音频压成密集条纹。
8. Canvas 可以在两次播放状态回报之间进行视觉插值以保持平滑，但不得独立推进或循环波形；下一次引擎位置回报必须校正画面。波形拖动继续按“指针位置 → 时间 → 对应 Deck 的 Seek 命令”工作，松开时才提交 seek。
9. 波形高度必须表达真实强弱包络。当前兼容旧缓存时先将平方根压缩峰值还原到线性振幅，再按整首歌的稳健动态范围映射；Canvas 同时绘制半透明连续包络和细竖线，使安静段、乐句与鼓点瞬态有明显高度差，禁止把峰值画成近似等高的装饰动画。
10. 同一次 PCM 解码同时执行节奏分析，输出 `bpm`、BPM 置信度、普通拍 `beats`、强拍 `downbeats`、小节起点 `bars` 和网格稳定度。界面以弱/中/强三档刻线显示，所有刻线与 mpv 的真实 `time-pos` 共用时间轴。
11. 分析在素材被扫描导入后以低优先级串行队列运行，不等操作员点击 Deck 才开始，也不并行解码多个大文件。扫描器必须先确认文件大小和修改时间稳定，避免分析仍在下载或复制的半成品；已完成结果持久化后，后续启动和装载歌曲只读取匹配文件指纹、算法版本和峰值密度的缓存。
12. 媒体库更新时 Deck 必须按稳定的文件路径/素材 ID 保持当前曲目，禁止保存数组下标作为身份。新文件导致排序变化时，不得重新装载、暂停或切换正在播放的 Deck。

波形缓存属于可重建派生数据，不写入媒体文件本身。分析失败不能阻塞歌曲导入或播放，应记录错误并允许后台重试；UI 在缓存尚未生成时显示明确的“波形分析中/不可用”状态。

UI 原型没有真实媒体文件时，可以使用确定性的演示峰值验证布局和动效，但必须在界面或开发说明中明确标注“演示峰值”，不得让其看起来像对应歌曲的真实分析结果。

### 节拍时间轴与联动总线

- mpv 的真实 `time-pos` 是唯一主时钟；波形动画、歌词、灯光和视频都不得建立各自独立的计时器。
- 每个 Deck 根据已缓存网格把播放器跨越的时间点转换为统一 `Beat`、`Downbeat`、`Bar` 事件。一次状态回报跨越多个拍点时依次补齐，暂停和后退不触发；大幅 Seek 只重置游标，禁止补放大量历史灯光事件。
- 事件包含 Deck、曲目稳定 ID、目标时间、观察延迟、BPM、置信度、Beat 序号以及是否强拍/小节。灯光和视频模块只订阅事件，不重新分析音频。
- 灯光预设后续可配置每拍、每 2/4/8 拍、强拍或每小节触发；视频切换可量化到下一拍、下一强拍或下一小节。
- 自动分析不是最终权威。每个 Deck 可以打开节拍网格校正面板，人工修改 BPM、拍号与首个小节第一拍，并以 10 ms 步长微调。校正数据保存到 SQLite `rhythm_correction`，加载分析结果时覆盖自动网格；波形、歌词以外的节拍标记、灯光和视频联动必须读取同一份校正后网格。
- 校正只改变派生时间网格，不改写 MP3/FLAC 文件。删除校正后可重新采用自动分析，媒体指纹变化时旧校正不得静默套用到新文件。
- 当前 UI 事件总线用于开发验证。正式 Tiger Touch Pro/视频联动必须迁到 Rust 高精度调度器，并按设备延迟提前发送；Windows UI 线程不能承担最终现场触发时序。

### 歌词分析与同步

- 优先读取同名 `.lrc`、媒体内嵌歌词或经授权的歌词文本；只有完全没有歌词时才进入人声分离和 ASR。
- 后台任务顺序为 Demucs 人声/伴奏分离、MOSS-Music 歌词识别与原生时间轴生成、人工快速校正，并保存 TXT、LRC 和逐词 JSON。开发与首版生产固定使用 `OpenMOSS-Team/MOSS-Music-8B-Thinking`，旧 ASR、强制对齐及其模型下载运行时全部退出当前技术基线，也不设置备用识别模型。
- Demucs 在 Windows Python 3.12 隔离环境使用 CUDA；MOSS-Music 通过 WSL2 内的 SGLang 服务使用同一块 NVIDIA GPU。模型权重固定保存在内置 D 盘，加载、推理和人声分离不得占用 UI 线程，不得暂停、重载或抢占正在播放的 Deck；新导入歌曲进入持久化任务队列，完成后再原子更新 SQLite 状态。
- 每个分析结果必须记录 ASR 模型 ID、模型版本/修订、分离模型版本、对齐模型版本和输入媒体指纹。只有媒体指纹或任一算法版本变化时才重新处理，已完成结果直接复用。
- Tauri 将任务保存到 SQLite `ai_analysis_jobs`，派生文件保存在应用数据目录的 `analysis/<media_fingerprint>/`。曲库扫描只串行登记任务，不直接加载 Python 或模型；Python 工作器一次租用一个任务。Demucs 两条已校验 FLAC 在分离阶段完成后立即持久化，使后续 MOSS 推理失败重试时不重复分离；歌词 TXT/LRC/逐词 JSON 在全部校验通过后再发布，最后原子替换 `manifest.json` 并把任务标记为 `ready`。
- 人声分离是歌词与原伴唱共用的一次性前置任务：`vocals` 送入 ASR，`no_vocals` 送入 Deck 伴唱音轨；两条消费者必须复用同一缓存，禁止重复分离同一首歌。
- 启动时通过 NVIDIA 驱动能力自动选择版本：有 NVIDIA GPU 为全功能制作播放版，无 NVIDIA GPU 为纯播放版。纯播放版禁止启动 Python、WSL、Demucs 和 MOSS，也不得给普通媒体登记制作任务；全功能版自动拉起 MOSS 和独立 Python worker，Windows 优先级为 Idle、并发固定为 1。worker 在模型加载期间保持等待，服务连接中断和限定次数内的结构化响应错误自动回队；应用中断的任务回到 `queued`，不丢失进度。生产安装包不得依赖开发目录中的虚拟环境，需另行封装并校验 Python 运行时、模型权重和第三方许可证。
- AI 队列采用非破坏性的三级调度：正在播放的歌曲为 0 级、已装入任一 Deck 的待播歌曲为 1 级、其余曲库为 2 级。播放开始不得杀死 Worker、MOSS 或暂停整条队列；Worker 保持 Windows Idle 优先级和单任务并发，当前任务完成后在安全点按级别领取下一首，避免中途终止造成模型重载或重复计算。旧版 `paused-for-playback` 任务在调度更新时自动恢复为 `queued`。
- MOSS 输入按最长 150 秒、8 秒重叠自动分段，输出时间戳回填整曲偏移并去重，避免长歌曲或 DJ 混音一次请求超过上下文。Demucs 已持久化的 stems 在重试中复用。
- `.kingsong` 是跨机器的单曲二进制交付格式，魔数为 `KSG1`、内部格式 ID 为 `club.king.kingsong`、首版为 1。包内顺序保存原唱、伴唱、LRC、逐句时间戳以及模型/管线来源，每个数据块使用 BLAKE3 校验；路径白名单、条目数、单文件和总解包尺寸都有硬限制。导入先在应用目录 staging 流式校验，完成后原子发布到本地媒体库和 `analysis/<fingerprint>/`，播放永远读取解包后的本地文件。
- Deck 的原唱源为原始媒体，伴唱源为通过审核的正式伴奏或缓存的 `no_vocals.flac`。当前实现由 mpv 在同一 Deck 内替换媒体源，并在文件就绪后恢复原来的 `time-pos`、暂停状态和音量；不得移动 Crossfader、自动开始播放或改变另一 Deck。未来若生成同时间轴多音轨代理，可改为按 mpv 音轨 ID 切换。
- SQLite 保存歌词来源、语言、行/词时间轴、置信度、人工校正状态、文件指纹和算法版本；媒体文件本身不因分析而被改写。
- 播放时 Lyrics Engine 只按同一个 mpv `time-pos` 查找当前行/词，因此暂停、Seek、切歌和双 Deck 独立播放不会失去同步。

## 7. 后续手机能力

手机端通过酒吧局域网访问本机服务，不直接控制播放设备。请求进入审核队列：

```text
手机提交 → 身份/桌号校验 → 频率与内容过滤 → 操作员审核 → 播放/上屏
```

即使后续允许自动通过，也必须保留总开关、撤回、黑名单和紧急清屏。公网访问、支付或会员系统不属于当前首版架构承诺。

## 8. 首轮技术验证清单

- 读取 Windows 显示器列表并稳定锁定 LED 输出目标
- 验证异形屏像素画布、遮罩和安全区
- 对真实素材完成播放、预览、切歌和原伴唱测试
- 验证完整 MP4、MP4 音频加替换视频、MP3 加循环视频三种组合的同步和回退
- 验证双 Deck 同时加载、手动 Crossfader、5 秒自动交叉淡化和连续多次切歌
- 验证从待播 Deck 的 IN 点启动、在当前 Deck 的 OUT 点触发，并跳过长前奏/结尾
- 记录交叉淡化中点音量、CPU/GPU 峰值、画面转场和灯光触发时序
- 验证 Qu-16 固件、USB/TCP MIDI、状态读取与目标动作
- 验证 Tiger Touch Pro 的版本和可用触发方式
- 验证主控电脑长时间播放的 CPU、GPU、内存和温度
- 拔网线、拔设备、关闭输出窗口和重启软件，验证安全状态

## 9. 主控电脑配置

以下是项目级要求，不是 Windows 自身的最低安装要求。目标是同时运行控制 UI、主屏合成/播放、实时预览、SQLite、Qu-16/Tiger Touch 适配器，并为后续 DJ 小屏和手机服务留出空间。

### 最低可用配置

适用于首版单主屏、常见 H.264/H.265 素材和基础文字叠加。采购新机时不建议再低于此档：

| 部件 | 最低要求 |
| --- | --- |
| 操作系统 | Windows 11 Pro 64 位，非 S 模式 |
| CPU | AMD Ryzen 5 7600/9600X，或同等级 6 核 12 线程 CPU |
| GPU | NVIDIA GeForce RTX 4060 8 GB，至少 2 个独立数字视频输出口 |
| 内存 | 32 GB DDR5，双通道 |
| 系统盘 | 1 TB NVMe SSD，TLC 优先 |
| 素材盘 | 2 TB NVMe/SATA SSD；不要长期从机械硬盘或移动 U 盘直接播放 |
| 网络 | 千兆有线网口；Wi-Fi 不能作为设备控制的唯一链路 |
| 电源 | 正规品牌 650 W、80 Plus Gold 或更高 |
| 散热 | 塔式风冷或可靠的一体水冷，机箱具备前后贯通风道 |
| 保护 | 1000 VA 以上 UPS，实际型号按整机与 LED 发送器功耗核算 |

### 推荐生产配置

这是当前建议采购的长期营业配置，兼顾性能余量、功耗和可维护性：

| 部件 | 推荐要求 |
| --- | --- |
| 操作系统 | Windows 11 Pro 64 位，专用本地播控账号 |
| CPU | AMD Ryzen 7 9700X（8 核 16 线程，65 W）或同等级产品 |
| GPU | NVIDIA GeForce RTX 5070 12 GB；如后续需要复杂多图层/多屏，可升 RTX 5070 Ti 16 GB |
| 内存 | 64 GB DDR5-6000，2 × 32 GB |
| 系统/应用盘 | 1 TB 高耐久 TLC NVMe SSD |
| 素材盘 | 独立 4 TB TLC NVMe SSD，避免系统更新和素材读取争用同一盘 |
| 备份 | 4 TB 以上外置 SSD/NAS，仅用于同步备份，不直接作为营业播放源 |
| 主板/网络 | 稳定型 B850/X870 主板，2.5 GbE；设备控制网络使用有线交换机和固定 IP |
| 视频输出 | 显卡原生 DP/HDMI 分别连接操作显示器和 LED 视频处理器，避免廉价分配器/USB 显卡 |
| 电源 | 750 W 至 850 W、80 Plus Gold、足额原生显卡供电接口 |
| 机箱散热 | 防尘、正压风道；保证高温酒吧环境下连续运行不过热降频 |
| 保护 | 在线式或纯正弦波 1500 VA UPS，同时保护主机、网络交换机和 LED 发送/处理器 |

RTX 4060 与 RTX 5070 均具备现代硬件视频能力；RTX 5070 官方规格明确支持 AV1 解码。当前约 354 万发光像素低于 3840 × 2160 的 829 万像素，因此推荐档的余量主要用于预览、图层、转场、未来第二输出和高码率素材，而不是因为主屏本身超过 4K。

### 采购与部署注意事项

- 不建议为本项目追求顶级游戏 CPU；稳定散热、SSD、电源和 UPS 更重要。
- 不进行 CPU/GPU 超频，关闭会导致不稳定的自动调优。
- 播控机不安装无关游戏、下载器、弹窗软件或第三方“电脑管家”。
- 禁止 Windows 通知、自动休眠、屏保和营业时自动重启更新。
- 显卡驱动验证后固定版本，不在营业前临时升级。
- BIOS 启用“来电自动开机”，并设置 Windows 自动登录专用播控账号及应用自动启动。
- 显示器通过设备标识绑定；启动时若 LED 屏缺失，保持安全黑场并报警，不把输出落到操作屏。
- Windows 输出窗口使用目标显示器的物理坐标与物理尺寸建立无边框顶层铺满窗口，不依赖系统 fullscreen 状态；这样可避免高 DPI 屏在热重连后产生隐形边框和边缘裁切。
- 建议保留一台可快速替换的备机，或至少准备已完成系统镜像的备用 SSD。

### 仍需随设备确认的接口

- LED 视频处理器/发送器已经可以作为普通 Windows 显示器使用；品牌型号不再阻塞首版，但维护档案中仍建议补录
- 控制显示器所需分辨率与接口
- Qu-16 的音频走 USB-B、模拟输出还是其他链路
- Tiger Touch Pro 和 Qu-16 是否与手机服务共用交换机，或划分独立控制网络

## 10. 尚未接受的架构决策

以下项目仍需通过验证后写入 ADR：

- Qu-16 使用 USB 还是 TCP MIDI
- Tiger Touch Pro 触发协议
- 主屏像素画布和异形遮罩格式
- DJ 小屏首版是否纳入
- 商用音乐供应商、授权范围与正式 API
- 在线播放、加密缓存和本地应急曲库的边界
